# Editable persona runtime: live validation, 9 November 2026

This report distinguishes a working runtime mechanism, useful collaboration, useful character development, and a complete engineering deliverable. They require different evidence. The [implementation design](editable-persona-models.md) describes the numerical model and execution protocol.

## Scope and method

The requested change was implemented on `feat/editable-persona-models` in a separate worktree. The original checkout, historical runs and existing deliverables were preserved. No unit tests were written or run. Validation used both actual builds (`cargo build --locked --bins` and `cargo build --locked --features desktop --bins`), the running desktop, real provider calls, actual host commands, exported files and independent numerical reproduction.

The primary request was exactly **“design smps for pc”**. A fresh state and empty working directory contained five general-purpose starting profiles: Mira, Oren, Sana, Ivo and Lena. No electrical professions, prior solutions or domain workflow were assigned. Each persona used Codex authentication with direct provider inference requesting **`gpt-6.1-sol`, `max`**. Reported model/effort receipts were checked. No engineering coaching or requirement amendments were injected into the run.

The coding assistant authored the starting profiles under the user's authorization. The CLI's default operator label `user` identifies the local initiating operator; it is not evidence that the human dictated those profiles. The exact task text came from the user.

The run spans recorded implementation revisions. Technical admission drains allowed current decisions/effects to finish before upgrades. This is iterative live validation, not a controlled comparison between two frozen implementations. All failed attempts, exact snapshots, responses, receipts, model bindings and exports remain retained.

## Primary run

The run ended naturally with all five participations stopped and no pending calls or effects. There were **153 provider calls: 143 accepted decisions and 10 rejected decisions**, with no provider failures in this cohort. All 153 receipts reported `gpt-6.1-sol`, `max`. The runtime completed 121 external effects, including 49 host commands (47 exit-zero and two exit-one observations) and 72 exact asset imports. Exit-zero was never treated as proof of engineering correctness.

It retained 94 current assets and six frozen deliveries, including Oren's separate supplemental review. Sana's integrated delivery contains **72 exact artifacts**, including every artifact from the other five deliveries. All 132 exported artifact entries across the six packages matched their retained content digests. No user acceptance or shared whole-supply sufficiency was asserted.

Reported usage was **5,862,368 input tokens and 761,223 output tokens: 6,623,591 total**, with 50,048 cached-input tokens included in the input count. Elapsed wall time was 02:29:33–04:16:30 UTC (106.95 minutes), including technical admission drains, upgrades and the personas' work. This is not the uninterrupted latency of a frozen release.

## Direct parameter editing and initialization boundary

A separate mechanics exercise explicitly instructed one fresh general-purpose identity, Rhea, using the same provider model and effort, to make a small reversible parameter edit and exercise matched assessment, activation, rollback, context excerpts and evidence delivery. It was kept out of the SMPS state and is not organic learning evidence.

Observed results:

- Three pending-model calls received the attributed seed but no task marker. The first active-model call received the actual task and no initial seed. Bootstrap resource selection was reset.
- The LLM changed exactly one literal parameter: `bias[row=11,column=0]`, the detail bias, from `0.40` to `0.45`.
- Two real, tool-free provider calls assessed old and candidate outputs against one matched hypothetical situation. Only the numerical detail output changed: `0.4218990052500079` to `0.46211715726000974`.
- A separate operation-free decision activated the observed candidate at epoch 2. A fresh call observed it. A later operation-free decision restored the exact original model digest at epoch 3.
- Unknown-context detail changed from `0.3799489622552249` to `0.4218990052500079`, then returned exactly. The other eleven outputs were unchanged.
- A 39-byte UTF-8 resource selected with `[12,24)` supplied exactly `café → Ω` in the subsequent request.
- The persona exported its evidence report and stopped voluntarily: 17 accepted decisions, one rejected decision, two completed assessment calls; all 20 terminal calls reported `gpt-6.1-sol`, `max`. Reported usage was 162,280 input and 46,615 output tokens, 208,895 total.

This establishes direct-edit and execution mechanics. It does not establish improvement, generalization or a useful long-term personality. The general provider LLM's weights were not modified: each persona's small numerical character network conditions the shared general reasoning model. There is no optimizer, gradient, backpropagation, fine-tuning service or training job.

The initial SMPS cohorts saw their task during bootstrap. Their first work decisions could therefore inherit task-influenced parameters or preparation. Their behavior cannot be attributed solely to numerical character. The later isolated initialization corrects and live-validates that boundary, without retroactively changing the original evidence.

## Failures, corrections and practical limits

The early prototype retained 20 accepted decisions, 17 rejected decisions and five locally canceled/provider-failed calls. It produced no host effects before the technical pause. Its reported usage was 183,739 input and 75,768 output tokens, 259,507 total. The five canceled calls have no reported final usage; any remaining remote work or charges are unknown.

Live failures led to corrections for bootstrap ordering, schema-version clarity, context choice during activation, prose prerequisites, nested local references, duplicate contribution proposals, resource-maintenance classification and portable export paths. Rejected responses produced no outbox effects or immutable state versions in the inspected primary and mechanics databases. Rejection feedback and original responses were preserved, and the personas repaired their decisions.

A follow-up live interface exercise confirmed that a registered, correctly shaped `asset.save` can execute when `available_tools` contains only `asset.read`, `asset.search`, `tools.describe` and `tools.search`. Its schema had been described in the preceding call but was deliberately not selected. Input validation remains mandatory. That exercise also exposed a missing retrieval path for forgotten receipt pointers; `history.search` now returns exact request/response/receipt references from authored or addressed events without replaying their bodies.

The follow-up actually used that lookup, read the original saved request and result, verified the unselected-schema operation and stopped. It used 14 accepted calls, all reporting `gpt-6.1-sol`, `max`, with 100,055 input and 22,485 output tokens (122,540 total). Its existing completed participation was not resumed; this was a separate attributed work item.

Context does not automatically replay conversation history. Exact selected resources and mandatory current state still became expensive: one primary request reached 2,450,706 bytes after selecting a large numerical report. The implementation now removes exact duplicate bodies, supports explicit UTF-8 excerpts, and reports context bytes and previous provider usage. There is no hidden quota or automatic semantic retrieval. This run does **not** establish economical context use or a cost advantage over the old implementation.

Reported tokens include rejected decisions. Across the primary run, failed prototype and both separate interface exercises, reported usage totals **6,308,442 input + 906,091 output = 7,214,533 tokens**. This includes 224 calls with final reported usage; five canceled prototype attempts have no final usage. Dollar charges were not reported by the provider; token counts are not a measured dollar bill. The older run had different conditions and is not a controlled cost baseline.

The desktop was built, opened against the live state and visually inspected. New state uses the editable-model view, with current calls, controls, conversations, personas, resources and exports. Existing onboarding still creates the earlier fragment runtime: initialize the new runtime through `./personas --neural`, then open it with `./personas --gui --progress STATE`. No migration of old state is claimed.

Admission drains, restarts and preservation of explicit stops were exercised. The run did not exhaustively inject every crash/network/filesystem fault. The architecture retains uncertain dispatches rather than automatically replaying them; that rule is not a claim that every external failure mode has been demonstrated.

## Verdict

The directly editable character-model mechanism, atomic adoption, explicit stopping, retained evidence, live tool execution and portable delivery export worked in the exercised cases. Voluntary collaboration produced substantive corrections and a coherent preliminary engineering package. The mechanical lifecycle was verified with actual model calls, including rollback and historical evidence recovery.

The experiment does not establish useful personality learning, causal behavioral benefit from the numerical networks, improved final-task performance over a controlled baseline, or economical operation. The initial bootstrap confound, zero organic parameter revisions, high token use and unfinished electrical implementation are material limits. This is a working implementation and an honest validation result, not proof that the new architecture already fulfills the broader personality-learning promise.
